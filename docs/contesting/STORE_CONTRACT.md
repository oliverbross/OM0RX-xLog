# Contest store contract

`XContestStore` is the durable local persistence boundary for the first contest pilots. It depends on Foundation, `XContestCore`, and the existing `CSQLitePrototype` system module. The scoring and rule target remains free of SQLite, UI, network, hardware, clocks, and identity generation. Its worker/UI fixture contract was approved and integrated at `603b770`.

## Database ownership

`SQLiteContestStore` requires an explicit file URL whose parent directory already exists. It has no default production path and does not create application directories. Each instance is an actor with one serialized connection. SQLite is opened in full-mutex mode with foreign keys enabled and a bounded busy timeout. Schema migrations and mutations run under `BEGIN IMMEDIATE`; a failed mutation rolls back all state, receipt, revision, QSO, and serial changes.

Schema version 2 stores sessions, complete drafts, canonical operations and durable receipts, serial counters and reservations, live or tombstoned QSOs, and an immutable QSO correction/deletion audit. Version 1 migrates to version 2 in one transaction; a failed migration leaves the version-1 schema intact. Workspace generation is a full UUID stored as SQLite `TEXT`; aggregate revisions remain unsigned integers. A session pins its complete rule identity, reference-data version, station/entity snapshot, operator list, display name, selected operator/category, generation, and aggregate revision. Codable snapshots prevent later reference-data changes from rewriting history. Unknown schema versions fail closed; only an explicit disposable-test harness may delete and recreate such a database.

## Mutation and recovery

Callers supply stable session, draft, request, reservation, QSO identities, generation UUIDs, and operation timestamps. The store creates none of these and does not consult a clock. Create uses a preallocated session ID, exact rule/reference identity, initial draft, and expected revision zero; its committed aggregate revision is one.

For every mutation, the store encodes a typed payload containing the operation kind and all semantic arguments with sorted JSON keys. The client `payloadDigest` is stored and returned for correlation, but it is not trusted as payload authority. The operation row stores a bounded immutable result: exact session/draft state, zero or one active reservation, scalar QSO count/points/multiplier count/claimed score, derived draft validation/dupe evidence, receipt, and the operation-specific reservation or committed-QSO evaluation. It stores only the committed QSO's bounded new-multiplier keys, never the full multiplier-label history or complete QSO log. Replay compares canonical bytes before decoding the typed result, so a cross-operation request-ID collision is a confirmed payload conflict rather than a corrupt/uncertain result.

Within one transaction the store first looks up `(sessionID, requestID)` and compares canonical bytes containing operation kind, session/generation/revision/draft scope, and semantic payload. Matching bytes return the original result and receipt even after mutable state advances. Different bytes reject the reused request ID. A new request then validates generation and revision, applies once, advances once, and writes the receipt atomically. Receipt recovery also checks the full generation UUID and correlation digest. A missing receipt remains unresolved; adapters must not invent success or a new request identity.

QSO correction and deletion follow the same replay-first rule. Their canonical payload includes the caller-created operation timestamp and required normalized reason; the store commit timestamp remains receipt metadata and is excluded from canonical retry identity. A matching retry returns the exact original bounded result even after a later correction, deletion, or reopen. A different payload under the same request ID conflicts before revision or target-state inspection. A new request against a tombstoned target returns an explicit deleted-QSO error.

Correction accepts a complete replacement contact, then preserves the QSO ID, session ID, original UTC timestamp, provenance, operator callsign, station location, and both raw and normalized sent exchange. The sent exchange is the durable allocated WPX serial or pinned WW sent zone. Remaining contact fields are editable, but the corrected QSO must pass semantic validation and the pinned contest rule. Delete keeps the QSO row as a tombstone. Each successful change appends an immutable audit record containing action, request ID, revision, reason, operation timestamp, commit timestamp, and complete before/after contact snapshots, fully rescores all live QSOs with `ContestEngine`, advances the aggregate revision once, and stores a bounded result containing no operating draft. Drafts, reservations, and serial counters are untouched, so allocated serials are never recycled.

## Drafts, serials, contacts, and reads

Draft updates persist the full `ContestDraftSnapshot` at the new aggregate revision. After WPX serial reservation, callsign, received exchange, report, entity, and other contact fields remain editable. The transmitted serial always remains fixed; band remains fixed only for band-scoped reservations, and transmitter identity remains fixed only for transmitter-scoped reservations. A temporarily mismatched positive frequency and band can be saved as an incomplete draft, is reported in the immutable validation projection, and must be corrected before commit. The draft and active reservation advance together. Reserve binds the formatted serial into the draft sent exchange. CQ WW rejects serial reservation before any counter mutation.

A reservation is bound to one session, draft, and normalized `session`, `band`, or `transmitter` scope. Counters increase atomically per scope. At most one active reservation may exist for a draft; reserved, transmitted, uncertain, committed, and void records remain in the ledger and numbers are never recycled automatically. Generic transitions cannot mark committed. CQ WPX operator-entry commit requires its valid reservation. QSO commit checks session, draft, scope, sent serial, and pinned session/rule/reference snapshots; it validates and fully rescores before atomically inserting the QSO, committing the reservation, clearing the draft, and advancing the revision.

Session and draft ordering is deterministic. The adapter requires exactly one draft and fails closed otherwise. `sessionReadSnapshot` and manager snapshots are coherent read transactions. Bounded `sessionPageSnapshot` returns session, drafts, active reservations, one log page, and score in one read transaction. Log pages order by timestamp then ID and cap page size at 1,000. Score and page coordinates carry session ID, full generation UUID, and revision; `ContestEngine` remains scoring authority.

Every live QSO read, log page, count, and score excludes tombstones. `qsoReadSnapshot` fences the expected full workspace-generation UUID and aggregate revision inside the same read transaction that returns the stored session and complete QSO, so later `contest_qso_get` adapters can expose every editable field with its immutable identity, UTC timestamp, provenance, operator/station identity, and sent allocation without a torn read.

The UI worker is an adapter for camel-case DTOs in `UI_CONTRACT.md`. UUID generation is emitted as canonical lower-case text on the wire. No store method transmits, keys, spots, calls a network service, or writes the normal logbook.

## Evidence limits

The Astra-approved pilot persistence baseline is committed at `c105b61`; its 23 focused native store tests passed. On 2026-10-17 the guarded macOS portable-manifest command for this P3 correction/delete candidate executed 32 `ContestStoreTests` with zero failures from the isolated contest-corrections worktree. That counted suite covers duplicate-credit promotion after correction and deletion, multiplier removal, full-score oracle equivalence, timestamp/UUID ordering, serial non-reuse, unchanged active draft/reservation state, exact replay after later mutation and reopen, canonical/cross-operation conflicts, workspace-generation and revision fences, coherent revision-bound reads, concurrent writers, structural and immutable-field rejection, post-write atomic rollback for correction and deletion, realistic version-1 migration preservation and failure rollback, and bounded history-independent results. This is local macOS evidence only. Current hosted macOS, Ubuntu, and Windows status and the exact acceptance boundary live in `PLATFORM_VALIDATION.md`. Backup/restore, performance targets, successful hosted three-platform acceptance at the final source commit, and integrated runtime/package acceptance remain separate work.
