## Confirmed findings

### RADIO-P6-001 — Medium / P2 — An inactive radio's selection publication changes the draft's sole power authority

**Current locations:** `Sources/XLogPrototypeSupport/LiveWorker.swift:559-593`, especially 585-587; `NativeDraftPowerGate.swift:57-65`, especially 62-64. Downstream consumption: `LiveWorker.swift:89-110`, `NativeDraftPowerGate.swift:113-125,143-169`.

**Trigger/call chain:** Both native per-slot selection owners publish independently. `prototype/src-tauri/src/station_selection.rs:209-235` includes the owner's fixed `radio_id`; `initialize:413-447`, optional `queue_power:294-326`, and worker bootstrap `331-399,853-858` can publish that owner's identity without making it active. Native `main.rs:2075-2085` initializes the explicitly requested slot, and `radio_slots.rs:set_active:122-141` / `main.rs:2216-2222` changes routing without updating this Swift power authority. Swift admits sequence numbers separately per radio but sends each accepted notice to one gate's `select`, which assigns its single `radioID`, provider and selection. Therefore Radio 2 metadata can replace Radio 1's power context while Radio 1 remains the active operating radio. A null fence from Radio 2's disconnect also clears the active Radio 1 context. Later active-radio reads may be coalesced by native optional publication and cannot reliably repair it.

**Impact:** With automatic TX power enabled, the draft can stop capturing the active radio's power after operating on the other slot. The gate subsequently chooses Radio 2's source rather than Radio 1's; exact source/session/frequency/mode fences still apply, so this does not prove arbitrary stale samples commit. The supported concrete outcome is missing active-radio capture; wrong-radio capture additionally requires that selected other source to emit an otherwise eligible measurement.

**Proof:** `actual-body-proof-run.log` records, from a freshly compiled verbatim current `NativeDraftPowerGate.swift`, `beforeInactivePublication=radio1`, `afterInactivePublication=radio2`, `afterInactiveDisconnect=nil`, with the native active-radio assumption held at Radio 1. This proof calls the actual gate primitive; the native call chain above establishes why an inactive publication can reach it. `Proof.swift`/`proof-run.log` also exercise current compiled module objects. No radio telemetry was fabricated into a production owner.

**Origin:** Pre-existing authority-design gap, not claimed as a new Phase 3/5 regression. Baseline power selection already had one global provider/selection. The CR-002 repair correctly gives sources independent slots and installs the exact routed agents, but it still does not convey the separate active-radio authority to the gate. `4353f538b462b201cd75967a1981ac64a33e3dfe` changes `select` to assign the incoming slot explicitly; unrelated source attach/reconnect/detach isolation is now correct. Existing registry test only tests inactive **source** changes, then explicitly selects Radio 2; it never exercises inactive **selection publications** or active routing.

**Fix direction:** Retain each slot's provider/selection metadata independently and select the draft's meter from an explicit generation-bound active-radio notification. Do not infer active authority from the last metadata callback. Add actual-worker publication tests for inactive connect/disconnect/handover and active switching while native optional notices are coalesced.

### RADIO-P6-002 — Medium / P2 — Failed FLEX retirement becomes a clean worker outcome and disables its normal retry path

**Current locations:** `Sources/XLogPrototypeSupport/LiveFlexSession.swift:180-183`, `221-259`; `LiveStationMethods.swift:51-56`; `LiveWorker.swift:388-427`; `Sources/XLogPrototypeWorker/main.swift:158-167`.

**Trigger/call chain:** A routed FLEX owner has an admitted owned PTT/Tune/CW duty. During worker retirement, `StationRadioRegistry.terminate` calls that exact owner's `terminate`. It sets `terminal = true`, then `try? await disconnect()` suppresses `release_unconfirmed` from `releaseOwned`. That failure deliberately retains the connection and obligation; `retireCurrent` never reaches `stopTransportOnly`. Registry termination returns `Void`, and worker outcome resolution depends only on online logs/contest spots. It can return `.clean` and `permitsRestart=true`. Normal release/disconnect IPC then fails immediately with `worker_stopping`, because the owner was marked terminal first.

**Impact:** Shutdown evidence falsely reports clean retirement although the transport and an unresolved release obligation remain. The ordinary release retry path is sealed; repeated terminal retirement can retry internally, but the successful worker path does not request that retry. A process exit eventually closes local resources; it does not establish observed RF-off. No claim is made that missing telemetry means real RF remained on. The distinction is between the release **attempt**, which did happen, and retirement **success**, which is lost.

**Proof:** Existing real `FakeFlexRadio` fixture was copied byte-for-byte from `LiveFlexSessionTests.swift:7-195`; it acknowledges the release but withholds a new off observation, matching the existing `testOwnedReleaseFailureRetainsConnectionAndObligationUntilObservedOff` contract. `proof-run.log`: `workerOutcome=clean permitsRestart=true ownerStillAttached=true commands=["ptt_on", "ptt_off"]`, then retry returns `worker_stopping`. `actual-body-proof-run.log` independently compiles verbatim current `LiveFlexSession.swift` (only an import of real neighboring support helpers is prepended) and reproduces terminal retention and rejected retry. No alternate implementation of the audited owner or safety helpers was supplied.

**Origin/scope:** `LiveFlexSession.swift` is unchanged across the remediation range; the swallowing behavior predates the repair. CR-002's original routing defect **is repaired**: an owned release is now attempted on the actual routed actor. This additional issue concerns outcome propagation and retained resources; it must not be described as the original omission of every release attempt. Root inspected Rust quit/module-switch admission separately; module-switch output-idle guards narrow active-output reachability and do not make a worker `.clean` receipt proof of successful FLEX retirement.

**Fix direction:** Return structured station retirement success/uncertainty to registry/worker; retain an explicit supported recovery/retry path while terminal acquisition admission remains closed. Do not map retained release failures to `.clean`.

## Rejected leads, safeguards and partial-depth limits

- **TCI same-target READY-only confirmation: unconfirmed concern, not a ranked defect.** `actual-body-proof-run.log` shows that an already-matching target can complete after only a newer READY message, because the session retains frequency/mode and refreshes generic configured evidence. `TCIWebSocketSession.swift:649-683,715-726,829-843`; `LiveTCISession.swift:203-245` projects generic evidence as radio freshness; native `manual_tune.rs:61-115,148-155` consumes it. However the demonstrated target was already correct. Reliable push-state retention and an intentional no-op policy are plausible; FLEX explicitly admits already-matching no-op tuning. No contradictory/stale accepted postcondition was demonstrated. Retain this as a test/provenance gap, not proof of wrong tuning.
- TCI reconnect/disconnect clears decoder/reducer/evidence and uses generation + lifecycle revision + connection identity. Exact receiver coordinates are checked; no automatic reconnect/replay follows tune failure. Receive-only controls do not create TX ownership. Filter confirmation additionally requires its own post-baseline evidence sequence. These safeguards reject several initially suspected stale-generation and fake-owner leads.
- FLEX parsing retains only followed-client slice candidates; frequencies are finite/ranged; explicit slice roles and separate interlock/RF-power observations gate controls. Reconnection invalidates observed state, pending command continuations are failed, timers canceled, and fresh interlock readback is distinct from unrelated slice updates. No live transport was opened to test these paths. Read ranges are recorded; full FLEX/IQ live receiver ownership was not exhaustively read or hardware-qualified.
- Agent connection power callbacks capture a unique event source and selected radio, and gate source IDs/sequence/session prevent old connections restoring detached state. Termination detaches only the owning slot. DB commit admission rechecks gate epoch and workspace/scope; successful emissions alone do not mark peaks durable.
- The non-process/default worker's `.shared` fallback does not prove an actual production-owner leak: production `processWorker` sets `ownsProcessSessions=true`; tests/acceptance have additional request guards. No synthetic injection was counted as real connection ownership.
- **Startup late-registration race: unverified scheduling concern.** Worker `main.swift:101-106` starts background initialization in a Task and immediately admits IPC; `startBackgroundServices:335-340` awaits another actor before capture registration. `LiveReferenceMethods:38-46` only schedules its work, so there is no intentionally long network wait at that boundary. Nevertheless no ordering barrier is shown in native `worker.rs:875-918`. An Agent connect that wins the race captures a nil gate (`LiveStationSession:315-335`) and performs its only source attachment at 343-344; later `installPowerCapture:232-235` merely assigns the property. Registry tests explicitly install before connecting and do not cover this ordering. No actual Agent connection was opened to reproduce the schedule, and no synthetic private-state injection was treated as proof. Keep this as an unverified race/test gap rather than a third ranked finding.
- Fldigi payloads are validated as a complete bundle before first TX, concurrent sends are rejected, generation checks stop later actions, and a release that overtakes pending TX cannot forget the duty until the sending attempt issues its own final RX. Generic stop failures remain uncertainty rather than proof of actual RF state.
- No fresh full package Swift build, sanitizer run, Linux/Windows execution, real CAT/TCI/FLEX traffic, RF, installed-app acceptance or production migration was performed. This is bounded source/test evidence, not an exhaustive security or station-safety qualification.
